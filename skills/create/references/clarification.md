# Clarification & Scope Guard

이 파일은 관문 **둘**을 담는다. 아래 "트리거 신호"~"비목적" 은 **Step 2.1**
(요청이 모호한가 — 초안 작성 *전*), 파일 하단의 "미결 게이트 (Step 3.1)" 은
**Step 3.1**(초안에 결정되지 않은 것이 남았는가 — 초안 작성 *후*) 이다.

## Step 2.1 — 모호성·스코프 가드

Step 2 와 Step 2.5 사이에서 호출되는 "이슈 본문 작성 직전" 안전망.
모호한 요청 / 과대 스코프를 1~2줄 확인으로 잡아낸다. 사용자가 명시적으로
"한 이슈로" 라고 답하면 그대로 진행한다 — 강제로 분리하지 않는다.

### 트리거 신호 (하나 이상 매치 시 확인)

1. **동사 없는 명사 나열** — 예: "사용자 관리 기능", "결제 시스템"
   → 무엇을 추가/변경/제거하려는지 1줄 확인.
2. **컴포넌트 3개 이상 혼재** — 한 요청에 백엔드/프론트/CLI/스킬 등
   3개 이상 영역이 동시에 등장 → 이슈 분리 제안.
3. **feature 범위 미정의** — 대화가 "X 어떻게?" "Y 도 필요" 식으로
   끝나서 acceptance criteria 가 도출 안 되는 상태 → 1줄 확인.
4. **verify prefix 후보** — "검증" / "verify" / "tracking" / "재개" /
   "context 유실" / "세션 단절" / "이슈 코멘트로 관리" 등이 사용자
   메시지에 등장하면 `verify` prefix 를 후보로 검토한다. 단 산출물이
   unit/integration 테스트 코드면 `test` (코드가 SSOT 로 더 강함).

위 신호 중 어느 것도 매치 안 되면 본 가이드는 no-op. 곧장 Step 2.5 로 진행.

### 스코프 과대 분리 제안 — 형식

여러 독립 기능이 한 요청에 들어 있다면, 묻기 전 분리안을 제시:

```
이것은 여러 이슈로 분리하면 좋을 것 같습니다:
  - feat(auth): 로그인 페이지
  - feat(profile): 프로필 수정
단일 이슈로 생성하시겠습니까? (y/n)
```

응답 처리:

- `y` / "한 이슈" / 묵시적 동의 → 그대로 한 이슈로 생성. 이때 본문
  Goals 에 분리안을 보존해 둔다 ("이후 PR 단위로 쪼갤 수 있음").
- `n` / "분리" → 가장 큰 범위 한 건만 이번에 만들고, 나머지는 사용자가
  /gh-issue:create 를 다시 호출하도록 안내. 자동 다중 생성 금지.

### 모호함 해소 — 형식

명사 나열·범위 미정의 케이스는 길게 묻지 말고 1~2줄로:

```
이슈를 생성하기 전에 한 가지만 확인:
- 이것은 <X> 를 <추가/수정/제거> 하는 작업으로 정리하면 될까요?
```

응답이 단답("응" / "yes")이라도 받으면 본문에 그대로 사용. 응답이
오기 전에는 절대 `gh issue create` 를 호출하지 않는다.

### 적용 범위 (Step 2.1)

이 가드는 `feat` / `refactor` / `chore` 처럼 스코프가 커질 수 있는
prefix 에 가장 자주 매치된다. `fix` / `docs` / `test` 는 보통 트리거가
발화하지 않으므로 no-op 된다.

### 비목적 (Step 2.1)

- REQ-ID 시스템 (`REQ-B-Access-1` 등) 도입하지 않음 — 프로젝트 특화
  포맷이라 범용 이슈 생성과 미스매치.
- multi-agent peer review (v1/v2) 도입하지 않음 — `gh-issue:create` 의
  단일-호출 계약과 충돌.

## 미결 게이트 (Step 3.1)

Step 3(본문 초안) 다음, Step 3.5/Step 4(생성) 앞에서 도는 두 번째 안전망.
Step 2.1 이 "요청이 모호한가"를 보는 반면 여기서는 "다 써 놓고 보니 결정되지 않은
것이 남았는가"를 본다. 무엇이 미결인지는 초안을 써 봐야 드러나므로 Step 2.1 에서는
잡을 수 없다 — 관심사가 다르므로 두 절을 합치지 않는다 (#1446 D-1).

이 저장소의 이슈는 사람만 읽는 문서가 아니라 **무인 실행의 입력**이다.
`gh-flow:issue` / `gh-flow:autopilot` / `gh-issue:proceed` 셋 다 실행 중에 사람에게
물을 채널이 없다. "이건 구현 시 결정" 이 남은 이슈는 그 지점에서 멈추거나, 근거 없이
추측해 진행하고 나중에 되돌린다. "나중에 정하자"가 실제로는 "정할 사람이 없는 곳으로
미루자"가 되는 셈이다 (#1436, AgentToolbox #2849).

`DISCUSSION_MODE=1` (`--as-discussion`) 이면 이 절 전체를 건너뛴다. RFC 는 결정 전
단계이고 `Open Questions` 가 산출물의 본질이다 (#1446 F-5).

### 미결 판정 기준

초안이 다음 중 하나라도 해당하면 미결로 본다:

1. `## Open Questions` 섹션이 존재하고 비어 있지 않다.
2. 본문에 "구현 시 결정" / "추후 결정" / "논의 필요" / "TBD" / "미정" 류 표현이 있다.
3. 판정 기준 항목이 판정 불가능하다 — 임계값·경로·형식이 비어 있거나 "적절히" /
   "필요 시" 로만 서술돼 있다.

3번이 필요한 이유: `Open Questions` 섹션을 쓰지 않고 본문 곳곳에 미결을 흩어 놓으면
1·2번만으로는 못 잡는다. #1436 의 "정확한 임계값·백오프 길이는 구현 시 결정하며" 는
설계 개요 본문에 있었다.

**2번의 `미정` 은 토큰 경계를 요구한다.** 부분 문자열로 잡으면 "김미정"(인명),
"장미정원", "범위 미정의"(Step 2.1 의 어휘) 가 전부 미결로 오탐된다. 이 게이트의
오탐 비용은 **이슈 생성 차단**이라 누락보다 비싸므로, 앞뒤가 줄 끝이거나 공백/구두점일
때만 매치하고 뒤에는 조사·서술형 어미(`이다`/`이며`/`이고`/`입니다`/`임`)만 허용한다 —
"미정임" 은 잡고 "미정의" 는 흘려보낸다. 나머지 표현들은 그 자체로 충분히 특이해
경계가 필요 없다 (PR #1455 리뷰).

**3번이 보는 섹션은 `수용 기준` 만이 아니다.** `feat` 외 템플릿은 판정 기준을 다른
이름으로 쓴다 — `fix`/`perf`/`refactor`/`test` 는 `## 검증`, `verify` 는
`## Verification Goal`. 게다가 이들은 체크박스가 아니라 평범한 불릿이다. 체크박스만,
그것도 `수용 기준` 아래만 훑으면 `feat` 이외의 모든 이슈가 3번을 통째로 우회한다
(PR #1455 리뷰). 체크박스든 불릿이든, 빈 항목·`...` 스켈레톤·"적절히"/"필요 시" 로만
서술된 항목이면 미결로 본다.

미결이 하나도 없으면 이 절은 **no-op** — 아무 출력도 내지 않고 곧장 Step 3.5 로
진행한다. 정상 경로에 잡음을 더하지 않는다.

### 협의 형식

길게 묻지 않는다. 미결 항목당 **선택지와 권고안**을 한 줄씩 제시한다:

```
이슈 생성 전에 결정이 필요한 항목이 있습니다:

1. <미결 항목> — 권고: <안> (근거: <한 줄>)
2. <미결 항목> — 권고: <안> (근거: <한 줄>)

이대로 확정할까요? 다른 결정을 원하시면 말씀해 주세요.
```

권고안을 먼저 내는 이유: "어떻게 할까요?"만 물으면 설계 부담을 사용자에게 되돌려주는
것이고, 대개는 권고안 그대로 확정된다.

응답이 오기 전에는 절대 `gh issue create` 를 호출하지 않는다.

### 확정 결과 기록

결정된 내용은 본문의 `## 확정 사항 (Decisions)` 섹션에 `<결정> — 근거: <한 줄>`
형식으로 남긴다. 그 섹션을 가진 템플릿은 `feat` 하나뿐이므로, 다른 prefix 로 분류된
초안에서는 게이트가 `## References` 바로 앞에 이 섹션을 **새로 추가**한다 — prefix 마다
기록 위치가 달라지면 후속 자동화가 기댈 곳이 없어진다 (PR #1455 리뷰). 원래 무엇이 미결이었는지 알아볼 수 있어야 한다 — 사용자가 나중에
뒤집으려면 무엇을 왜 그렇게 정했는지가 본문에 남아 있어야 하기 때문이다.

| 상황 | 표기 |
|---|---|
| 사용자가 확정 | 표기 없음 |
| `--no-ask` 자율 결정 | `(자율 판단)` + 근거 한 줄 |
| 사용자가 "그냥 만들어" | `(보류 — 사용자 지시)` |

### `--no-ask` 자율 결정 규칙

무인 호출(`gh-flow:autopilot` Step 0b 등)은 묻지 않는다. 대신 다음 순서로 스스로 정한다:

1. 저장소의 기존 관례·상수·인접 구현에서 값을 유추할 수 있으면 그것을 따른다.
2. 없으면 **가장 보수적인 쪽** — 기능을 덜 켜고, 실패 시 안전한 쪽 — 을 택한다.
3. 어느 쪽도 불가능하면 그 항목만 수용 기준에서 빼고, 별도 이슈 대상임을 본문에
   명시한 뒤 진행한다.

세 경우 모두 `확정 사항` 에 `(자율 판단)` 표시와 근거 한 줄을 남긴다. 어떤 경우에도
체인을 멈추지 않는다 — 멈추면 막으려던 실패를 스킬 안으로 옮기는 것뿐이다.

### 응답 처리

- **일부 항목만 답함** → 남은 항목만 다시 묻는다. 임의 보완 금지.
- **"그냥 만들어" / "알아서 해"** → 게이트를 통과시키되 미결을 `확정 사항` 에
  `(보류 — 사용자 지시)` 로 기록한다. 무시하고 지우지 않는다. **이 탈출구는 사람이
  자기 이슈에 대해 내리는 결정 전용이다** — `--no-ask` 는 절대 이 표기를 만들지
  않는다. 표기만 붙은 미결은 여전히 미결이고, 무인 소비자에게 필요한 것은 라벨이
  아니라 실행 가능한 선택이기 때문이다 (PR #1455 리뷰). 무인 호출은 아래 D-4
  사다리로만 처리한다.
- **`--no-ask` 인데 1·2번으로도 못 정함** → 위 3번대로 처리하고 진행한다.
